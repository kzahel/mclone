# L0 - Lighting oracle foundation

Standing after the durable lighting reference in [`../lighting.md`](../lighting.md). This is the first lighting-system tactical. It implements the oracle substrate needed to validate the future solver before porting `LevelLightEngine`.

## Goal

Extend the existing Minecraft 1.17.1 integration oracle so it can capture and compare vanilla stored light:

- decode `BlockLight` and `SkyLight` `DataLayer` byte arrays from Anvil chunk sections
- expose the vanilla `isLightOn` validity flag alongside persisted light bytes
- preserve section-Y and missing-vs-present light data exactly
- emit light facts in committed fixtures alongside the existing block/biome/heightmap data
- add reusable comparison helpers for byte-exact light-section diffs
- prove the fixture path with one pinned seed/chunk generated by the official 1.17.1 server

At the end of `L0`, we should be able to say: "for this vanilla chunk, these are the exact sky/block light bytes Minecraft persisted." The TypeScript light solver does not exist yet.

## Why this slice first

Lighting has two independent risks:

1. whether we can reproduce vanilla's propagation algorithm
2. whether we can observe vanilla's expected output accurately

`L0` solves only the second risk. It lets later slices run our solver against Minecraft's own block layout and compare only light. That is important because same-seed end-to-end lighting is only meaningful after the chunk block contents match too.

The first high-value validation mode is:

```text
official MC server chunk blocks + official MC server light
  -> hydrate MC blocks into a TS test level
  -> run our future light solver
  -> compare TS light bytes to MC light bytes
```

That isolates lighting bugs from worldgen bugs.

## Fixture shape

Add light as its own chunk field rather than mixing it into `sections[]`.

Recommended JSON shape:

```jsonc
{
  "chunkX": 0,
  "chunkZ": 0,
  "status": "full",
  "isLightOn": true,
  "sections": [/* existing block sections */],
  "heightmaps": {},
  "biomes": [],
  "light": {
    "block": [
      { "y": 0, "dataBase64": "..." }
    ],
    "sky": [
      { "y": -1, "dataBase64": "..." },
      { "y": 0, "dataBase64": "..." },
      { "y": 16, "dataBase64": "..." }
    ]
  }
}
```

Rules:

- `y` is the signed section `Y` byte exactly as stored in NBT.
- `dataBase64` encodes exactly 2048 bytes.
- preserve missing arrays by omitting that layer's section record.
- do not synthesize all-zero sections.
- sort each layer by `y`.
- keep the existing block `sections[]` sparse and block-only.

Base64 is preferable for committed fixtures because two 2048-byte arrays per section are noisy as JSON number arrays. Tests should still decode base64 back to exact bytes before comparing.

## Decode rules

For every entry in `Level.Sections`:

1. Read signed `Y`.
2. If `BlockLight` exists:
   - require byte-array length `2048`
   - preserve its raw byte order
   - store under `light.block`
3. If `SkyLight` exists:
   - require byte-array length `2048`
   - preserve its raw byte order
   - store under `light.sky`
4. Independently decode block `Palette` / `BlockStates` only when present, using the current path.

`Int8Array` signedness should not change the fixture bytes. Convert with byte-preserving `Uint8Array` views when serializing or comparing:

```ts
new Uint8Array(raw.buffer, raw.byteOffset, raw.byteLength)
```

Do not interpret nibbles during fixture extraction except in tests that specifically verify `DataLayer` indexing.

## Comparison helper

Add an oracle-light comparison helper that accepts two chunk-light records and returns structured differences.

Suggested shape:

```ts
interface LightSectionBytes {
  readonly y: number;
  readonly data: Uint8Array;
}

interface ChunkLightBytes {
  readonly sky: readonly LightSectionBytes[];
  readonly block: readonly LightSectionBytes[];
}

interface LightDiff {
  readonly layer: "sky" | "block";
  readonly y: number;
  readonly kind: "missing" | "extra" | "byte_mismatch";
  readonly firstByteOffset?: number;
  readonly expected?: number;
  readonly actual?: number;
}
```

The helper should:

- compare section presence by `(layer, y)`
- compare `data.length`
- compare all 2048 bytes
- report at least the first mismatch offset
- be usable later from solver tests without depending on fixture JSON shape

This can live under `src/oracle/integration/light-fixture.ts` or another oracle-local module. Keep it shared enough for future tests.

## Server oracle plan

Use the existing official-server harness for the first fixture:

```bash
./oracle/integration/gen-fixture.sh \
  --seed 12345 \
  --chunks 0,0 \
  --out test/fixtures/integration/overworld-seed-12345-chunks-0-0.json
```

`0,0` is intentionally the first target because the current server runner only guarantees startup/spawn-area generation. Do not make L0 depend on arbitrary far chunk generation.

If `reference/minecraft-1.17.1/server.jar` is missing, the harness should use `scripts/fetch-server-jar.sh 1.17.1`. If that download fails because the sandbox cannot reach Mojang hosts, request escalation and rerun the same command.

## Implementation status

L0 landed as the oracle substrate only:

- `src/oracle/anvil/chunk.ts` now decodes `BlockLight` and `SkyLight` byte arrays from every raw Anvil section entry, including light-only padding sections without a block palette.
- `DecodedChunk.isLightOn` and fixture `chunk.isLightOn` expose vanilla's persisted light-validity flag from `Level.isLightOn`.
- `src/oracle/integration/chunk-fixture.ts` serializes present light sections under per-chunk `light.block[]` and `light.sky[]` arrays.
- `src/oracle/integration/light-fixture.ts` owns base64 DataLayer encoding/decoding and reusable byte-exact comparison helpers.
- `test/fixtures/integration/overworld-seed-12345-chunks-0-0.json` is regenerated through the official 1.17.1 server harness and now includes persisted vanilla light bytes.
- `oracle/integration/gen-fixture.sh` runs the TypeScript dumper with Node transform-types support, and `scripts/fetch-server-jar.sh` verifies SHA1 portably on this platform.

## Tests

Add focused unit coverage before generating large fixtures.

### Anvil decode tests

- section with `BlockLight` length 2048 decodes one block light record
- section with `SkyLight` length 2048 decodes one sky light record
- section with both layers decodes both records
- section with light but no `Palette` is retained in `light` and omitted from block `sections[]`
- missing light tags produce no records
- byte arrays with length other than 2048 throw
- signed bytes roundtrip to the same unsigned byte values

### Fixture tests

- base64 serialization/deserialization returns exact bytes
- light sections are sorted by `y`
- committed light fixture has full chunk status and all light data arrays decode to 2048 bytes
- existing non-light fixtures remain readable if `light` is absent

### Comparison tests

- identical light records produce no diffs
- missing section reports `missing`
- extra section reports `extra`
- byte mismatch reports the first mismatched offset and values
- layer mismatch does not collapse sky/block together
