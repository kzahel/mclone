# 025: Render Section Visibility Graph

Status: first implementation landed; follow-up needed for outside-retained-section traversal seeding and graph-build timing.

## Purpose

Port Minecraft Java 1.17.1's `VisGraph` / `VisibilitySet` section occlusion culling and use the new native perf lanes to measure its effect before and after integration.

This is not a mesh simplification pass and not greedy meshing. It is a visibility traversal pass over already compiled render sections.

## Reference Source

Read before implementation:

- `reference/minecraft-1.17.1/src/net/minecraft/client/renderer/chunk/VisGraph.java`
- `reference/minecraft-1.17.1/src/net/minecraft/client/renderer/chunk/VisibilitySet.java`
- `reference/minecraft-1.17.1/src/net/minecraft/client/renderer/chunk/ChunkRenderDispatcher.java`
- `reference/minecraft-1.17.1/src/net/minecraft/client/renderer/LevelRenderer.java`

Key Java facts:

- `ChunkRenderDispatcher.RenderChunk.RebuildTask.compile(...)` creates one `VisGraph` per 16x16x16 render section.
- While scanning section blocks for model/liquid rendering, it calls `VisGraph.setOpaque(...)` for blocks where `BlockState.isSolidRender(...)` is true.
- `VisGraph.resolve()` produces a `VisibilitySet`, a 6x6 face-connectivity matrix.
- `LevelRenderer` uses that matrix during breadth-first visible-section traversal. It does not run a global offline PVS.

## Algorithm Shape

Per render section:

1. Track a 4096-bit opaque/visited mask for the section's 16x16x16 cells.
2. Mark solid-render cells opaque.
3. For every non-opaque boundary cell, flood-fill through non-opaque cells.
4. Record which of the six outer section faces each connected empty region touches.
5. For every face pair touched by the same region, mark those faces mutually visible in `VisibilitySet`.

Output granularity is one `VisibilitySet` per render section:

```text
WEST can reach EAST? yes/no
WEST can reach UP? yes/no
NORTH can reach SOUTH? yes/no
...
```

This is similar in spirit to Quake-style PVS but much smaller and dynamic. Quake stores broad offline leaf visibility; Minecraft stores local section face connectivity and recomputes it when a render section is rebuilt.

## Cost Model

Expected per-section computation is small:

- block scan: already happens during section mesh compilation
- opaque mask: 4096 bits, 512 bytes
- flood-fill worst case: visits up to 4096 cells once
- neighbor checks: at most 4096 * 6
- edge starts: 1352 boundary cells
- scratch queue: up to 4096 integer indices, roughly 16 KiB if stored as `u32`
- result: 36 booleans, cheaply stored as a `u64` bitset

This work runs when a render section is compiled/recompiled, not every frame. Runtime traversal should only read the compact `VisibilitySet`.

## Update And Storage Policy

The visibility graph is derived data:

- compute it when building or rebuilding a CPU render section
- keep it beside the cached CPU render-section mesh/state
- upload nothing extra to the GPU for the first slice
- do not persist it to disk
- do not put it in chunk snapshots or protocol messages

If a chunk load/unload or block/liquid/light mutation marks a render section dirty, rebuild that section's mesh and `VisibilitySet` together. Since the current dirty scope is chunk-wide, first integration can recompute all sections in the dirty chunk; section-granular dirtying can follow once deltas carry section coordinates.

## Implementation Slices

### 1. Pure Data Structures

Add renderer-side or mesh-side pure types:

- `SectionFace` or reuse a small direction enum mapped to Minecraft direction order
- `VisibilitySet`
- `VisGraph`

Keep them independent of `wgpu`.

Preferred storage:

- opaque/visited mask: `[u64; 64]`
- queue: reusable `VecDeque<u16>` or fixed `Vec<u16>` plus head index
- face set: `u8`
- visibility matrix: `u64`

Implemented in `native/crates/mclone-mesh`:

- `SectionFace`
- `VisibilitySet`
- `VisGraph`
- `TexturedRenderSectionMesh.visibility`

### 2. Oracle Fixtures

Add a Java oracle helper that calls the real Minecraft classes:

- construct `net.minecraft.client.renderer.chunk.VisGraph`
- call `setOpaque(new BlockPos(x, y, z))` for synthetic opaque cells
- call `resolve()`
- print the six-by-six `VisibilitySet.visibilityBetween(...)` matrix

Fixture cases:

- empty section: all faces visible
- fully solid section: no faces visible
- single solid wall splitting X: west/east blocked, same-side face pairs still connected
- west-east tunnel: west/east connected, unrelated outer faces blocked unless touched
- L-shaped tunnel: touched faces connected through the bend
- enclosed internal cavity: no outer faces visible from that cavity

Implemented fixture:

- `test/fixtures/render/visgraph-synthetic.json`
- generated by `pnpm --silent oracle:gen visgraph --seed 0`
- current cases: empty, fully solid, lightly opaque early-out, X wall, west-east tunnel, enclosed cavity

### 3. Native Parity Tests

For every Java fixture, assert native `VisGraph.resolve()` produces the exact same 6x6 face matrix.

Also add direct native tests for edge behavior:

- coordinate indexing matches Java: `x | z << 4 | y << 8`
- less than 256 opaque blocks returns all-visible, matching Java's early-out
- completely full section returns all-not-visible

Implemented in `cargo test -p mclone-mesh`.

### 4. Render Integration

Store `VisibilitySet` with cached render sections. Then replace the current "iterate all section AABBs and frustum-test them" draw-list selection with a traversal stage:

1. Identify one or more starting sections near the camera.
2. Breadth-first traverse neighbor render sections.
3. Keep frustum culling as a required filter before drawing.
4. When moving from section A to neighbor B, consult A's `VisibilitySet` and the source/exit directions like Java's `LevelRenderer.RenderChunkInfo`.
5. If visibility is blocked, skip traversal into that neighbor.

Keep the first integration conservative: if a section lacks neighbors or the camera starts inside an ambiguous/solid section, prefer not over-culling. Incorrectly drawing extra sections is acceptable during bring-up; incorrectly hiding visible terrain is not.

Implemented first pass:

- `TexturedSectionDrawResources` stores the per-section `VisibilitySet` beside uploaded GPU section meshes.
- The draw path and `textured_section_visibility_stats` use the same graph-aware traversal.
- Empty mesh sections inside retained chunk snapshot height are kept as traversal nodes but are not uploaded to the GPU.
- Timedemo loads an effective static scene radius of `max(chunk_radius, path_radius_chunks)` so the default orbit stays inside retained sections.
- Traversal falls back to frustum-only if the camera starts outside the retained section set.
- Current limitation: Java seeds traversal from visible in-range chunks when the camera has no render chunk; native still uses frustum-only fallback for that ad-hoc outside-retained case.

## Out Of Scope

- Greedy meshing
- portal/PVS precomputation beyond local section connectivity
- GPU occlusion queries
- persistence of visibility graphs
- changing mesh vertex/index output
- Java exact traversal if it would temporarily hide visible terrain; prefer conservative native traversal first, then tighten
