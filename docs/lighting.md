# Lighting

Research and implementation notes for Minecraft Java 1.17.1-style lighting in `mclone`.

This document is a reference for the future lighting implementation. It is not a tactical slice by itself. The solver should be a direct TypeScript port where the data/algorithm are parity-critical, while the scheduling and transport around it should fit the existing host/worker/render-world architecture.

## Goals

- Match vanilla 1.17.1 stored light behavior for the overworld.
- Keep the light solver authoritative-host owned, not renderer owned.
- Feed meshing workers with packed light facts so `ModelBlockRenderer` and `LiquidBlockRenderer` stop using constant sky/block light.
- Keep browser main-thread work limited to GPU upload, frame submission, and lightmap texture updates.
- Preserve one logical worker protocol shape for browser singleplayer, remote browser clients, Node hosts, and storage; oracle tests may exercise the solver below the host service boundary.
- Leave room for alternate render lighting backends without making vanilla stored light a renderer-only feature.

## Vanilla Model

Minecraft stores two independent light layers:

- `LightLayer.SKY`: sky light, source level 15 from sky-accessible columns.
- `LightLayer.BLOCK`: emitted block light, source level 0 by default and up to 15 for emitting blocks.

`LevelLightEngine` owns one `BlockLightEngine` and one `SkyLightEngine`. Querying raw local brightness combines them as:

```java
max(blockLight, skyLight - skyDarken)
```

The visible renderer does not compute light propagation. It reads packed per-vertex light values, then samples a client-side 16x16 lightmap generated by `LightTexture`.

Vanilla stored light is also gameplay data. Blocks and entities query it for rules such as spawning, crop/mushroom growth, snow/ice melting, daylight detectors, and other light-sensitive behavior. A future raytraced renderer can replace how pixels are lit, but a vanilla-parity world profile still needs vanilla-style stored sky/block light unless gameplay parity is intentionally disabled too.

## Stored Data

Light is stored per 16x16x16 section in `DataLayer`.

- One `DataLayer` is 2048 bytes.
- It stores 4096 4-bit light values.
- Index order is `y << 8 | z << 4 | x`.
- Each value is a normal exposed light value, `0..15`.

The graph solver internally inverts this:

```text
internal level 0  = full light
internal level 15 = dark
stored value      = 15 - internal level
```

This is why `LayerLightEngine.getLevel(...)` and `setLevel(...)` are full of `15 - value`.

Vanilla light sections are not exactly block sections. `LevelLightEngine` adds one section of padding above and below the world:

```text
minLightSection = minSection - 1
lightSectionCount = worldSectionCount + 2
maxLightSection = minLightSection + lightSectionCount
```

That padding matters for sky propagation and client/server light packets. `mclone` should model light sections separately from non-empty block sections, even if the first snapshot format stores them beside chunks.

## Dirty Inputs

Vanilla queues light work from three main places.

### Chunk Boundary Footprint

Lighting is not an isolated per-chunk calculation. Block light falls off by one level per transparent block, so a level-15 source can affect blocks up to 15 blocks away. A chunk whose light is correct for rendering therefore needs the neighboring chunk data that covers that footprint, especially for emitters or openings near chunk borders.

`mclone` currently loads a `viewDistance + 1` chunk ring. That one-chunk halo is enough for block-light propagation into the visible view, but the solver work for that halo must still be scheduled cooperatively. Running the whole halo to idle in one host command recreates the D6 chunk-load stutter under a new name.

Sky light has a different shape: straight vertical sky columns are mostly column-local, but side propagation around roofs, cave mouths, and chunk-edge openings still crosses chunk boundaries. Missing chunks must not be treated as transparent final data for a published lit chunk; either the neighboring data is present for the solve, or later authoritative light deltas must correct the result when it arrives.

### Block Changes

`Level.setBlock(...)` compares old and new states. It queues `checkBlock(pos)` only when the change can affect light:

- `getLightBlock(...)` changed
- `getLightEmission()` changed
- old or new state uses shape-based light occlusion

`checkBlock(pos)` checks the changed block and all six neighbors, because light crossing any adjacent face may have changed.

### Section Empty/Non-Empty Transitions

`LevelChunk.setBlockState(...)` watches whether a `LevelChunkSection` changes empty status. On transition, it calls:

```java
lightEngine.updateSectionStatus(sectionPos, sectionIsEmpty)
```

This tells section storage whether that 16x16x16 area should have a light data layer.

### Chunk Lighting

At `ChunkStatus.LIGHT`, `ThreadedLevelLightEngine.lightChunk(...)`:

- marks the chunk not light-correct
- marks non-empty sections active with `updateSectionStatus(..., false)`
- enables sky-light sources for the chunk column
- scans known emitting block positions and calls `onBlockEmissionIncrease(...)`
- runs propagation
- marks the chunk light-correct

During worldgen, `ProtoChunk` records emitting positions as blocks are placed. On load from storage without trusted light data, `ChunkSerializer` can rescan the chunk for emitters.

## Propagation Algorithm

The core is `DynamicGraphMinFixedPoint`, an incremental fixed-point graph relaxation over block-position keys.

Important structures:

- 16 queues, one per internal light level.
- `computedLevels`, a pending target-level map.
- `firstQueuedLevel`, the brightest pending level.

The algorithm is not a naive breadth-first flood fill every time. It incrementally repairs the graph.

High-level behavior:

```text
checkNode(pos):
  checkEdge(pos, pos, darkest)

checkEdge(source, target, candidate):
  compute target's best level from its source and neighbors
  enqueue target if its desired level differs from stored level

runUpdates(budget):
  while work remains and budget remains:
    pop the brightest queued target
    if target should become brighter:
      store brighter level
      notify neighbors with increase=true
    if target should become darker:
      enqueue target for the darker value
      set target temporarily dark
      notify neighbors with increase=false
```

This two-direction repair is why torch removal works: neighbors that depended on the removed torch darken, while neighbors with another valid source path find it during recomputation instead of blindly going dark.

## Block Light Rules

`BlockLightEngine` treats `Long.MAX_VALUE` as the self/source node.

For an emitting block:

```text
internal source cost = 15 - getLightEmission(pos)
stored source value = getLightEmission(pos)
```

For neighbor propagation inside the solver:

- missing chunks behave as opaque/dark as an internal fallback, not as final publishable lighting for a normal chunk snapshot.
- if the target block opacity is `>= 15`, propagation stops.
- if adjacent face occlusion shapes block the face, propagation stops.
- otherwise cost increases by `max(1, targetOpacity)`.

Through plain air, cost increases by 1, so a level-14 torch naturally becomes 13, 12, 11, and eventually 0.

This depends on existing block-state hooks:

- `BlockState.getLightEmission()`
- `BlockState.getLightBlock(level, pos)`
- `BlockState.useShapeForLightOcclusion()`
- face occlusion shapes

A temporary opacity-only implementation would be a known parity gap. The direct port target includes shape occlusion.

## Sky Light Rules

Sky light has two pieces:

- section/column source bookkeeping in `SkyLightSectionStorage`
- propagation math in `SkyLightEngine`

For columns with sky sources enabled, vanilla finds the highest stored light section in the chunk column and seeds its top layer from the synthetic source.

The special sky rule is vertical:

```text
straight downward through transparent blocks can stay level 15
sideways or obstructed travel decays by at least 1
opaque or face-occluding blocks stop propagation
```

This is what makes open shafts bright deep underground, while caves behind stone roofs become dark.

## Section Storage And Notifications

`LayerLightSectionStorage` keeps:

- `updatingSectionData`: mutable data used by the active solver pass.
- `visibleSectionData`: immutable-ish snapshot used by readers.
- `changedSections`: sections whose light data changed.
- `sectionsAffectedByLightUpdates`: sections whose downstream consumers need notification.
- `queuedSections`: loaded light data waiting to be accepted.
- `toMarkData` / `toMarkNoData` / `toRemove`: section lifecycle queues.

After propagation, `swapSectionMap()` copies the updating map to visible storage, then calls:

```java
chunkSource.onLightUpdate(layer, sectionPos)
```

In vanilla:

- server `ServerChunkCache.onLightUpdate(...)` marks a `ChunkHolder` light section dirty.
- `ChunkHolder.broadcastChanges(...)` sends `ClientboundLightUpdatePacket`.
- client queues the received `DataLayer`s and marks render sections dirty.

For `mclone`, this maps cleanly to:

- host marks authoritative light sections dirty.
- host emits `chunk_snapshot` baselines and later `chunk_delta` light updates.
- render-world worker ingests light facts and marks affected render sections dirty.
- mesh workers rebuild section meshes using the latest light data.
- main thread uploads rebuilt meshes and updates the existing `LightTexture`.

## Architecture For `mclone`

Vanilla has a shared heap and a `ThreadedLevelLightEngine` wrapper. We do not have that shape in browsers, and we should not simulate it with renderer-owned state.

The intended ownership is:

```text
authoritative host worker / Node host
  owns chunks, block edits, light engine, light data, dirty light sections
  schedules light work with cooperative budgets
  emits snapshots/deltas

render-world worker
  owns client-side read-only chunk cache plus light snapshots
  marks sections dirty when block or light facts change
  builds mesh input neighborhoods for mesh compilation

mesh worker
  reads block + biome + light neighborhood facts
  emits packed vertices with vanilla packed light values

browser main thread
  owns WebGPU buffers, bind groups, frame submission, LightTexture
  never runs light propagation
```

This is an architectural divergence from vanilla only in scheduling and memory ownership. The light values, propagation rules, source rules, section indexing, and packed render values should remain vanilla-shaped.

## Backend Boundaries

Do not hide lighting behind scattered constants. Define an explicit world/profile lighting mode and route all solver access through a small service boundary.

Recommended split:

```ts
export type WorldLightMode = "vanilla17" | "none";
export type RenderLightingMode = "vanilla_lightmap" | "fullbright" | "raytraced";
```

`WorldLightMode` controls authoritative stored light:

- `vanilla17`: default; runs the ported `LevelLightEngine`, persists light sections, and exposes `getBrightness(...)` for simulation.
- `none`: debug/custom profile only; no vanilla light parity, no vanilla light-sensitive gameplay guarantees.

The generated-world host currently exposes this as `lightingMode?: "vanilla17" | "none"`. The default is `vanilla17`; `none` is only for debug/custom profiles and future backend experiments.

`RenderLightingMode` controls presentation:

- `vanilla_lightmap`: default raster path; mesh workers bake packed sky/block light into vertices and the main thread samples `LightTexture`.
- `fullbright`: debug path; useful before the solver is ready or when isolating geometry/material bugs.
- `raytraced`: future renderer path; may ignore baked packed-light values for pixels, but should still be able to consume authoritative world light if gameplay/profile requires it.

This keeps the future RTX/raytrace option open without weakening the MVP parity target. The first implementation should still land `vanilla17` as the default world light backend, because it is the only backend that matches Minecraft's simulation and current raster meshing expectations.

Shape the host/runtime API around an interface, not direct class construction:

```ts
interface WorldLightEngine {
  readonly mode: WorldLightMode;
  checkBlock(pos: BlockPos): void;
  updateSectionStatus(section: SectionPos, empty: boolean): void;
  enableLightSources(chunk: ChunkPos, enabled: boolean): void;
  runUpdates(budget: number): number;
  getBrightness(layer: LightLayer, pos: BlockPos): number;
  getRawBrightness(pos: BlockPos, skyDarken: number): number;
  drainDirtyLightSections(): readonly DirtyLightSection[];
}
```

The `vanilla17` implementation should be the direct port. The `none` implementation should be small and explicit, not interleaved through the solver.

## Data Contract

Add light as chunk facts, not as renderer-only state.

Recommended packed records:

```ts
export interface PackedLightSection {
  readonly y: number;
  readonly data: Uint8Array; // 2048 bytes, vanilla DataLayer layout
}

export interface PackedChunkLight {
  readonly sky: readonly PackedLightSection[];
  readonly block: readonly PackedLightSection[];
  readonly lightCorrect: boolean;
}
```

Then extend `PackedChunkSnapshot` with optional light initially:

```ts
readonly light?: PackedChunkLight;
```

Once lighting is authoritative, make it required for lit chunks.

For `WorldLightMode: "none"`, snapshots may omit `light`; consumers must treat that as a declared non-vanilla profile/debug mode, not as partially loaded vanilla light.

For deltas, use section-level replacement first:

```ts
export interface ChunkLightDelta {
  readonly type: "chunk_light_delta";
  readonly chunkX: number;
  readonly chunkZ: number;
  readonly light: {
    readonly sky?: readonly PackedLightSectionUpdate[];
    readonly block?: readonly PackedLightSectionUpdate[];
  };
}
```

Where a section update can be either a 2048-byte `DataLayer` replacement or an explicit empty section. This mirrors vanilla light packets with `YMask` and `emptyYMask` without copying the exact packet shape into the engine protocol.

Do not put light into mesh payloads as the source of truth. Meshes should contain packed vertex light values derived from current light facts.

## Scheduling Design

The vanilla `ThreadedLevelLightEngine` batches chunk-priority tasks and runs:

```text
PRE_UPDATE tasks
run light propagation
POST_UPDATE tasks
```

For `mclone`, keep the semantic split but use the host scheduler:

```text
light job queues:
  preUpdate:
    section status changes
    queued saved light data
    chunk sky-source enable/disable
    chunk light initialization

  propagation:
    LevelLightEngine.runUpdates(budget)

  postUpdate:
    block checkBlock calls from live edits
    schedule another propagation slice if postUpdate enqueued graph work
```

Dirty light-section publication should happen after propagation swaps the visible section map. Vanilla's live `checkBlock` tasks are `POST_UPDATE`, so the graph work they create is picked up by a later scheduled light update rather than the already-running propagation pass.

Use a cooperative budget, not `Integer.MAX_VALUE`, in browser workers. Node can use the same budgeted runner for consistency.

Recommended host policy:

- prioritize chunks by current player/session chunk interest.
- keep input/poll/player-state work ahead of lighting.
- process lighting in bounded slices.
- publish chunk snapshots only after required initial lighting completes for that chunk.
- publish light deltas after dynamic edits or delayed propagation slices complete.

For initial MVP generated terrain, it is acceptable for a chunk job to generate terrain and then finish initial lighting before publishing the chunk. Live block edits need incremental light deltas.

### Worker Boundary

The current browser implementation runs generation, world ticks, persistence, and light propagation inside the generated-world worker. That is a tactical simplification, not the target architecture. It prevents main-thread stalls, but lighting can still starve the authoritative world worker and delay chunk publication, water ticks, and player-state responses.

The target architecture is a dedicated lighting service/worker owned by the authoritative host. See [`lighting-worker-architecture.md`](lighting-worker-architecture.md) for the full worker boundary, protocol, mailbox, revisioning, neighbor readiness, and migration plan. The core rule is that normal terrain chunks should be published once with initial light included; do not publish unlit geometry as a loading shortcut.

## Interaction With Meshing

The translated renderer already expects vanilla packed light:

```text
packedLight = (sky << 20) | (block << 4)
```

`ModelBlockRenderer` and `LiquidBlockRenderer` call `LevelRenderer.getLightColorFromState(...)`, which reads `level.getBrightness(LightLayer.SKY/BLOCK, pos)` and applies block emission. Today the level implementations mostly return constants. Lighting should replace those constants in the client/render-world level.

Meshing needs a neighborhood, not just one section:

- face lighting samples adjacent blocks.
- ambient occlusion samples edge/corner blocks around a face.
- liquid rendering samples current and above positions.
- chunk-boundary faces need neighbor chunk light data.

So render-world dirty section rebuild readiness should treat missing neighbor light data the same way it already treats missing neighbor block data.

When a light section changes, dirty at least the matching render section and neighboring sections whose meshes may sample across the boundary. Vanilla marks sections affected in a 3x3x3 cube around changed block positions; `mclone` can initially dirty the changed section plus adjacent sections and tighten from measurement later.

## Validation

Use both unit-level source parity and rendered-pixel validation.

Unit tests:

- `DataLayer` nibble indexing and clone behavior.
- block light from a torch in open air: 14, 13, 12, ... 0.
- torch removal darkens only nodes that lack an alternate source.
- two overlapping sources preserve the brighter path.
- solid block insertion/removal repairs neighbor values.
- sky light stays full in an open vertical shaft.
- sky light decays sideways into a cave mouth.
- section boundary propagation works in all six directions.
- missing neighbor chunks are not published as final transparent light; boundary publication waits for neighbor inputs or explicitly tests a non-final opaque/dark fallback.

Oracle tests:

- Generate a Java 1.17.1 server chunk, read `BlockLight` and `SkyLight` NBT section arrays, and compare `DataLayer` bytes.
- Include one open daylight terrain chunk, one cave-heavy chunk, and one structure/feature fixture with emitted blocks when those sources are live.
- Add an oracle for dynamic edits later by applying a small block script in Java, ticking light updates, and dumping changed light sections.

Browser validation:

- Run the smallest probe that reaches real generated terrain with lighting.
- Save screenshots to `/tmp`.
- Inspect daylight terrain, shadowed caves, an open skylight shaft, and a torch-lit enclosed room.
- Verify the main thread does not run light propagation in the performance trace.

## Known Risks

- Shape occlusion is parity-critical and can be expensive if implemented with heavyweight object graphs in hot loops. Port the behavior, then optimize representation if measurement demands it.
- Sky light source bookkeeping is easy to get almost right. Preserve the light-section padding and top-section logic from `SkyLightSectionStorage`.
- Chunk boundaries are the most likely source of visual seams. Tests need cross-chunk sources and cross-chunk sky openings.
- Full initial lighting can delay chunk publication. The host scheduler must prioritize by current interest and budget work so player/session updates remain responsive.
- A GPU-compute light solver is not the first implementation. It would complicate authority, persistence, oracle testing, and Node parity. Consider it only after a direct CPU port is correct and measured.
